# 个人代码库维护协议

本目录是用户跨项目复用的个人代码知识库,跟带教项目里的 `doc/`、`AI痕迹/` 无关。
条目只写进本 skill 的 `knowledge/`,不写进被带教的项目。

## 何时触发

用户出现以下意图时执行本协议(不需要完整原话):

- 把这段常用代码 / 这个 API / 这个函数收进我的代码库
- 维护代码库、入库、记下来以后用
- 核对这段用法对不对,对了就写入知识库

带教过程中,L2「该用哪个函数」应先查 `knowledge/INDEX.md`,有现成条目就指向它。

## 三步流水线(必须按序,不可跳步)

### 1. 核对

对照官方文档(或该语言/框架的权威来源),检查用户给的符号、参数名、默认值、类型是否正确。

- 对的:明确说「这部分是对的」。
- 错的:先纠正,再入库。纠正时写清「你写的是什么 → 实际是什么 → 依据」。
- 用户给的不完整:补全常用参数,不要只存用户随口提的那几个。
- 拿不准:标「待核实」,不要编造默认值。

### 2. 去重

读 `knowledge/INDEX.md`,再打开可能撞车的条目文件。

| 情况 | 动作 |
|------|------|
| 已有同一符号(同语言+同库+同函数/类) | 合并进旧条目:补缺的参数、纠正旧错误、追加例子;更新「入库记录」 |
| 名字像但不是同一个(例如 `Column` vs `mapped_column`) | 新建,并在双方「和它一起出现的」里互链 |
| 完全新 | 按 `_TEMPLATE.md` 新建 |

去重键:`语言 + 库/模块 + 符号名`(符号名用官方拼写,全小写做文件名)。

### 3. 写入

1. 按模板写或改条目(常用参数必须补全:必填、类型、默认、词源、含义、易错点)。
2. 更新 `INDEX.md`(分类、一句话用途、文件链接)。
3. 把补全后的卡片给用户看一遍,尤其是纠正过的默认值。
4. 在 skill 仓库提交:`git add knowledge/ SKILL.md README.md` ,建议信息 `knowledge: 收录 <符号名>`。
   用户说「提交 / 推送」时再 `git commit` 和 `git push`;没说就只改文件并给出建议提交信息。

## 条目要求

- 词源:拆英文(或缩写)帮助记忆,格式与用户习惯一致,例如 `primary (主要) + key (键) = 主键`。
- 常用参数写全,冷门参数放「进阶」,不要为了短而漏掉真正常用的。
- 最小例子必须能直接看懂,不写脱离真实用法的玩具。
- 不写绝对路径、密钥、账号。
- 默认值必须是官方默认,不是「我常用的值」。

## 目录与命名

```
knowledge/
├── PROTOCOL.md              # 本协议
├── INDEX.md                 # 总索引,每次入库必更新
├── _TEMPLATE.md             # 新条目模板
└── {语言}/{库或主题}/{符号}.md
```

- 语言目录用小写:`python/`、`javascript/`、`java/`、`sql/`。
- 库目录用官方常用名:`sqlalchemy/`、`fastapi/`、`react/`。
- 文件名 = 符号的官方拼写,全小写,点改成连字符:`mapped_column.md`、`use-state.md`。
- 一个符号一篇,不要把整个库塞进一个文件。

## 带教时怎么用

- L2 工具提示:先搜 INDEX,命中则让用户打开对应条目,而不是另写一份解释。
- 用户卡在某 API:可以问「要不要把这个收进代码库」。
- 入库是独立动作,不占用当前任务卡,做完立刻回到原来的带教任务。
